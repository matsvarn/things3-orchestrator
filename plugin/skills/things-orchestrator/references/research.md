# Source capture

Use this branch for a thread, changelog, document set, source packet, or requested mode. It owns research, progress, form, and one complete commit.

A source packet is not automatically a dump. Actual use is not installed inventory. Keep each named client separate. Check relevant thread replies. Collapse aliases and optional methods that lead to one durable artifact.

Organizing future skill or mode work in Things is capture. It is not authority to author that skill now.

## Research quietly

1. Name one decision and durable result. If creation is authorized and one result remains, commit this turn. Ask only when two supported results or Things forms remain.
2. Send one opening update. Batch independent reads. After that, report only a blocker, material scope change, or owner choice. Never preview the next lookup.
3. Use direct sources, then one suitable fallback. Use an offered authenticated browser before marking a source unavailable.
4. Make a private coverage list. Give every named source, relevant reply, topic, and local evidence scope one fact, uncertainty, or exclusion and one destination.
5. Learn enough now to shape the work. Put concise facts under `## Starting evidence` on the Task that consumes them. A source read removes a `Read` Task, not an unfinished evidence result.
6. For a clearly new result, do not call `things_read` or browse Areas.

## Build one source document

Create one Project with `document=source`. Use the owner's first-person viewpoint. The Project note has nonempty `## Result`, `## Done when`, and `## Guardrails` blocks.

Every nested Task has a natural action title and a concrete `finish`. The server renders each finish as `## Leave with`. Put extra `## Starting evidence`, `## Method`, constraints, and `## Sources` in `notes_markdown`; never add another Leave-with block. Use at most one native checklist, with at most three finite checks, on the cross-client test or delivery Task that needs it. Testing every active client is one Task, not one Task per client. Do not turn evidence lists into checklists. Full URLs do not consume the prose limit. Each Markdown section stays below 800 prose characters; the complete note can be longer. Split titles that join two actions with and or then. `Review and mark the proposed rules` is one allowed review result.

For three or more sources, give each a short bold label and its full URL. Keep sources on the Task that uses them. An optional tool or method is never a Task; put it in the consuming Task's method notes. A product changelog for setup belongs on the delivery Task, not a separate evidence Task. Continual work stays outside the finite Project.

For six or more Tasks, use two to four natural native headings. Keep the source document at 20 native rows or fewer: one Project plus headings, Tasks, and checklist rows. Near that limit, use three headings or one evidence Task per source family; never delete a distinct required output. Evidence comes before conclusions. The collapsed Project must explain the path. Every opened Task must be startable without this chat.

For an artifact that encodes the owner's behavior, keep separate Tasks for: representative owner evidence; actual tools and standing instructions; repeated patterns and corrections; external candidate evidence; comparison; proposed rules; owner rule review; draft; draft review; tests in every active client; one real-use validation; delivery. Omit only an output that already exists. Use one external-evidence Task per source family, not one Task per idea. Add finite fixes only after a review or test finds them.

Map every accepted requirement and Done-when clause to completed research, the Project note, one Task, or outside. A pin, publish, send, or install Task is delivery; do not add another delivery Task. When one artifact needs setup in several clients, use one result title such as `Deploy the skill across my clients`; put install and pin checks in its checklist.

Before the first commit, confirm every Task has `finish`, every source is labeled, and the whole document is present. Send the source Project as the only mutation. If the server returns `next=revise`, fix the payload in this turn without asking the owner. After `applied`, report the Project, home, Task count, first Task, and unavailable evidence. Stop. Never offer a later notes pass.

Done when every source is accounted for and the accepted Project lands with all Project and Task notes in one intent.
