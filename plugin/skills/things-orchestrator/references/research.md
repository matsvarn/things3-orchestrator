# Source capture

Use this branch for a thread, changelog, document set, source packet, or requested mode. It owns research, form, progress, and creation through one commit.

A source packet is not automatically a dump. Preserve evidence scope. Actual use is not installed inventory. One named client cannot replace another. A named thread includes relevant replies. Collapse aliases and methods that lead to the same durable artifact.

Organizing future skill or mode work in Things is capture. It is not authority to author or update that skill now. Keep the work in the Project.

## Run one quiet transaction

1. Name the decision and one durable result that the sources must support.
2. Check authority. A source packet without create authority writes nothing. If one supported result remains and creation is authorized, continue through the commit this turn. Ask only when two supported results or Things forms remain.
3. Send one opening update that names the result. Batch independent reads. Stay silent during routine research. Report only a blocker, material scope change, or owner choice.
4. Use direct suitable sources. Use one suitable fallback when a source fails. Use an offered authenticated browser before calling that source unavailable. Name unavailable evidence. Never invent it. Unavailable evidence is not a form question; keep its accepted evidence result as a Task.
5. Make a private coverage list. For every owner-named source, relevant reply, topic, and local evidence scope, record one material fact, material uncertainty, or exclusion and its destination: done now, Project note, Task, or outside.
6. Separate shaping research from Project work. Learn enough now to name and structure the work. Put concise facts learned now under `## Starting evidence` on the Task that consumes them; do not save only URLs or make the owner find the same facts again. Starting evidence seeds future work. It does not make a future audit, comparison, or artifact complete. A source read now removes a `Read` Task, but not an unfinished evidence result.
7. For a clearly new result, start with the named sources. Reserve `things_read` for requests that mention existing or possibly open work. Never browse Areas during create.

## Write the Things document

Use the owner's words and first-person viewpoint inside Things. Write `my chats` and `I approve`, not `the owner` or system narration.

The Project title names one durable result. Add the artifact type when a label can name a workflow, mode, or skill. Natural does not mean terse.

For a substantial Project note, use only the useful Markdown blocks:

```markdown
## Result
## Done when
## Guardrails
```

Use natural native headings that describe the owner's path. For six or more Tasks across distinct stages, use two to four headings.

Each Task title says what the owner will do and what visible result it produces. Put evidence before its conclusion.

For a source-backed artifact that encodes the owner's behavior, keep this visible Task path: actual tools and standing instructions; repeated patterns and corrections; external candidate evidence; compare and propose rules; owner rule review; draft; draft review; representative tests in every active client; one real-use validation; delivery. Omit a Task only when its output already exists. Do not combine adjacent outputs in one title, note, or checklist. Do not pre-create generic fix or revision Tasks; add finite fixes only after a review or test finds them.

A concrete final action such as pin, publish, send, or install is delivery. Do not add a generic delivery Task after it.

Before commit, check the artifact path privately. Point each required output to a different Task title, in order. Rewrite the plan if one output is missing or one Task owns adjacent outputs. Confirm the Project title names the artifact type. Confirm each evidence, source, comparison, and review Task has `## Leave with`; each source Task also has `## Starting evidence` and `## Sources`.

For a substantial Task note, start with `## Leave with`, then add only needed `## Starting evidence`, method, constraint, or `## Sources` blocks. Use a native checklist for finite substeps that share one Task finish. Put committed later work in Project Tasks, not note checkboxes.

For three or more sources, give each a short bold source label and put its full URL on the next line. Put sources only on the Task that uses them. Put an owner-named optional tool in the consuming Task's method notes. Do not make it a Task, a deliverable, or leave it outside the Project. Continual work stays outside a finite Project.

Leave undecided work outside active Tasks. A pin, repository, client, or extraction method is evidence or delivery unless the owner accepts a separate result.

Apply two tests before commit:

- **Collapsed view:** title, headings, and Task titles explain the complete path with notes closed.
- **Opened Task:** the note lets the owner start and recognize the result without reopening the chat.

Map every accepted requirement to completed research, a Project note, one Task, or outside. Every `## Done when` condition must already hold or have one Task. Keep the complete supported finish path visible in dependency order.

Commit once. The normal final reply names the created home, first Task, and unavailable evidence. Routine creates apply at once; follow the server if it requests approval.

Done when every named source and evidence scope has a fact or exclusion, the Project passes both tests, and every accepted Things change is in the one commit.
